# Compiler

基于 **C++17、Qt Widgets 和 qmake** 的编译原理教学演示程序。项目提供图形界面，用于输入源程序、查看 Token 串、构建 LL(1) 分析表、填写符号表、生成四元式、执行基本块内的 DAG 优化，以及输出单寄存器风格的目标代码文本。

项目适合阅读编译流程和开展小规模实验。源语言由外部文法文件定义，目标代码是用于展示的指令文本，仓库没有配套的汇编器、链接器或执行器。

> **当前运行前提：**源码依赖运行工作目录中的 `TextFile/grammar.txt`，但当前仓库未包含 `TextFile/` 目录和该文法文件。克隆代码后，仍需补齐与语义动作匹配的原始文法，才能验证完整编译流程。本文没有把根据代码推导的示例标记为实际运行结果。

## 功能与编译流程

| 模块 | 当前代码中的功能 | 结果入口 |
| --- | --- | --- |
| 源程序输入 | 文本框输入，或通过文件对话框读取 `.txt` 文件；输入字符检查 | 主窗口“输入代码” |
| 词法分析 | 扫描关键字、界符、标识符、常数、字符/字符串常量 | 主窗口“Token串” |
| 语法分析 | 从文法文件计算 FIRST、FOLLOW、SELECT 集，检查候选式 SELECT 集冲突，构造 LL(1) 表并进行栈式预测分析 | “语法分析结果”窗口及文本文件 |
| 符号表 | 记录函数、整型形参、局部变量、类型信息和活动记录 | “符号表”窗口 |
| 中间代码 | 通过语义栈生成算术、赋值、条件、循环、函数与返回相关四元式 | “四元式”窗口左栏 |
| 优化 | 划分基本块，构造 DAG，复用公共子表达式，处理赋值标记和直接常量运算 | “四元式”窗口中栏 |
| 目标代码 | 读取优化后的四元式，处理变量活跃信息、寄存器状态及跳转回填 | “四元式”窗口右栏 |

点击主窗口“确定”后，代码按以下顺序执行：

```text
文本框 / .txt 文件
        │
        ▼
输入字符检查，末尾追加 #
        │
        ▼
SynAna::AN()
  ├─ 读取 grammar.txt，构造 LL(1) 分析表
  ├─ 按需调用 WordAna 扫描 Token
  ├─ 执行 SymbolTable 符号表动作
  └─ 执行 createquat 四元式动作
        │ 语法分析返回成功
        ▼
optimize::run() → optQuat.txt
        │
        ▼
ObjectCode::scan() → ObjectCode.txt / 内存中的 Object
        │
        ▼
点击“下一步”，选择结果页面
```

词法分析是在语法分析过程中按需推进的；主窗口没有单独的“只执行词法分析”按钮。后续页面主要显示已经生成的数据，不会重新编译输入。

## 获取与构建

### 1. 获取代码

```bash
git clone https://github.com/Leohugo0405/Compiler.git
cd Compiler
```

不使用 Git 时，也可以下载仓库 ZIP 并解压。

仓库同时包含 `WordAnalysis.h` 与 `wordanalysis.h`。在通常不区分大小写的 Windows 文件系统上，它们可能合并为一个文件或产生检出警告。两者内容相同且未被当前工程使用，但后续维护时应统一命名。

### 2. 使用 Qt Creator 构建

1. 安装 Qt 开发环境及相匹配的桌面编译工具链。
2. 在 Qt Creator 中打开仓库根目录的 `Compiler.pro`。
3. 选择桌面 Kit，确认 Qt、编译器和目标架构匹配。
4. 执行 qmake 并构建项目。
5. 在项目的运行设置中，将**工作目录**设为准备好 `TextFile/` 的目录，例如仓库根目录。
6. 按下一节补齐运行文件后，再执行编译实验。

如果 Qt Creator 使用独立构建目录，运行工作目录可能不是源码目录。可执行文件位置与运行工作目录是两个独立设置，不能只把文法放在源码旁就假定程序能找到它。

### 3. 使用命令行构建

以下是 Windows MinGW Kit 的命令示例，应在该 Qt Kit 对应的命令行环境中执行。命令说明构建步骤，不代表当前仓库已完成构建验证。

```bat
mkdir build
cd build
qmake ..\Compiler.pro
mingw32-make
```

使用 MSVC Kit 时，应换用相匹配的 MSVC 开发环境和构建工具，例如 `nmake`；不要混用 MinGW 的 Qt 库与 MSVC 编译器。

生成程序的位置取决于 Kit 和构建配置，Windows 下常见为 `debug\Compiler.exe` 或 `release\Compiler.exe`。可从仓库根目录通过实际路径启动，保持运行工作目录正确，例如：

```bat
build\debug\Compiler.exe
```

程序没有实现通过命令行指定源文件、文法文件或输出目录的接口。

## 文法文件约定

`SynAna::GetLL1Table()` 从硬编码路径 `TextFile\\grammar.txt` 读取文法。文法没有嵌入 `.qrc`，也没有从 GUI 选择其他文法的入口。

读取器要求：

1. 用空格分隔每个符号。
2. 每组规则以左部非终结符开头，不写 `->`。
3. 同一左部的不同右部用 `|` 分隔。
4. 每组规则以 `#` 结束。
5. 非终结符使用 `<名称>`，空产生式使用 `<空>`。
6. 分析栈固定从 `<函数>` 开始；FOLLOW 初始化使用文法文件中第一个左部，因此应让第一组规则的左部与开始符号一致。

例如，下面仅展示读取器接受的**规则书写格式**，不是完整文法，也不能直接替代缺失的文件：

```text
<表达式> <项> <表达式尾> #
<表达式尾> + <项> <表达式尾> | <空> #
```

文法中的语义动作分两类：

| 动作类型 | 代码识别方式 | 执行对象 |
| --- | --- | --- |
| 符号表动作 | 以双引号开头的动作符号，例如 `"函数名"` | `SymbolTable::callAction()`，接收当前 Token |
| 四元式动作 | 以 `$` 开头的动作符号，例如 `$PUSHi$` | `createquat::action()`，接收上一个已匹配 Token 的值 |

构造 FIRST/FOLLOW/SELECT 时，动作符号被排除；预测分析压栈时则保留并执行它们。因此，动作插入位置会影响符号表和四元式结果，不能仅补一份普通的 C 语言文法。

`<标识符>` 和 `<无符号整数>` 在分析器中是两个特殊终结符，占位匹配 Token 类型 `I` 和 `C`。虽然名字叫“无符号整数”，扫描器的 `C` 分支还包含其他数值形式；这不代表这些形式能在后续优化和代码生成中正确处理。

## 核心模块与算法

### 1. 词法分析：WordAna

`wordana.cpp` 维护关键字表 `K`、界符表 `P`、标识符表 `I`、常数表 `C`、字符/字符串表 `S` 和用于展示的 `Tokens`。

| 类型 | 含义 | 显示形式 |
| --- | --- | --- |
| `K` | 关键字 | `(K 1)` |
| `P` | 运算符、括号等界符 | `(P 11)` |
| `I` | 标识符 | `(I 1)` |
| `C` | 数值常量 | `(C 1)` |
| `S` | 字符或字符串常量 | `(S 1)` |
| `END` | `#` 结束标记 | 设置 Token 为结束状态，不追加到展示串 |

表地址从 1 开始。`global.h` 还定义了 `UNKNOWN` 类型。`WordAna::scan()` 跳过空格、换行和制表符，按首字符分派给标识符、数值、字符串或界符扫描函数；双字符界符优先尝试匹配。

扫描器包含十进制、十六进制、科学计数法和小数的识别分支，但 GUI 字符检查、扫描器实现和后续处理并不完全一致，使用边界见下文。

### 2. 语法分析：LL(1) 预测分析

实际实现是**分析表驱动的栈式预测分析**；`synana.h` 中“递归子程序分析”的旧注释并不准确。

主要步骤：

1. 读取文法，分离用于集合计算的产生式和保留动作符号的产生式。
2. 迭代计算 FIRST 集和 FOLLOW 集。
3. 按右部能否推出空串计算 SELECT 集。
4. 检查同一左部的候选式 SELECT 集是否相交。
5. 构建以非终结符和当前输入符号为索引的 LL(1) 分析表。
6. 以 `#`、`<函数>` 初始化分析栈，匹配终结符、展开非终结符并执行语义动作。

`LL1Table.txt` 内部使用从 0 开始的产生式下标，非法表项初始化为 `-1`；部分产生式列表和 SELECT 展示编号则从 1 开始，阅读输出时应区分。

### 3. 符号表与活动记录

| 数据结构 | 主要内容 |
| --- | --- |
| `SYNBL` | 标识符名字、类型指针、种类、地址指针 |
| `TAPEL` | 类型值、类型信息指针；当前构造函数只初始化 `int` |
| `PFINFL` | 函数层次号、区距、参数个数、参数表指针 |
| `VALL` | 活动记录条目，初始含 `OLD SP`、返回地址、全局 display 地址 |

已注册动作包括 `"函数名"`、`"int形参名"`、`"int变量名"` 和 `"参数串结束"`。种类标记分别使用 `f`（函数）、`vf`（形参）、`v`（局部变量）。

当前模块主要执行表项追加和地址指针记录，没有完整的作用域解析、重复声明检查、未声明标识符检查或类型兼容性检查。

### 4. 四元式生成

`quat` 的四个字段为 `op`、`arg1`、`arg2`、`result`，显示为：

```text
(操作符,操作数1,操作数2,结果)
```

未使用字段通常填 `_`，临时变量依次命名为 `t1`、`t2` 等。

| 动作 | 生成内容 |
| --- | --- |
| `$PUSHi$` | 将标识符或常数压入语义栈，不直接生成四元式 |
| `$GEQadd$`、`$GEQsub$`、`$GEQmul$`、`$GEQdiv$` | `+`、`-`、`*`、`/` 运算 |
| `$ASSI$` | `=` 赋值 |
| `$LOGIC$` | 从栈中取比较运算符和操作数，生成比较结果 |
| `$IF$`、`$EL$`、`$IE$` | `if`、`el`、`ie` 控制标记 |
| `$WH$`、`$DO$`、`$WE$` | `wh`、`do`、`we` 循环控制标记 |
| `$FUN$`、`$RET$`、`$FUNEND$` | `fun`、`ret`、`endfun` |

`do` 在这里是循环控制中间标记，不能据此推断完整支持源语言的 `do ... while` 语法。

### 5. 基本块与 DAG 优化

`optimize::run()` 将原始四元式转换为内部结构，划分基本块，逐块构造 DAG 并写出优化结果。

- 赋值被归为类型 0。
- `+ - * / > <` 被归为类型 2，用于构建运算节点。
- 其他操作被归为类型 3，控制标记参与块边界处理并保留输出。
- 通过节点主标记和附加标记管理赋值关系，优先用非临时变量作为主标记。
- 查找操作符、左右操作数相同的节点，实现块内公共子表达式复用。
- 对两个直接数值操作数的 `+ - * /` 调用 `calcu()`，使用 `toInt()` 进行整数常量计算。

这是局部优化实现，没有全程序优化、SSA 或跨块数据流优化。常量除法采用整数除法，且没有除零检查，不能作为可靠的浮点优化器使用。

### 6. 目标代码生成

`ObjectCode::scan()` 读取 `optQuat.txt`，调用变量提取、活跃信息处理和指令生成逻辑。代码以一个逻辑寄存器 `R` 为中心，由 `RDL::R` 和 `RDL::active` 记录状态，使用栈 `SEM` 保存待回填的控制流位置。

源码中的目标指令/标记包括：

- 数据传送：`LD R,x`、`ST R,x`。
- 算术：`add`、`sub`、`mul`、`div`。
- 比较：`gt`、`lt`、`eq`、`ne`、`ge`、`le`。
- 控制流：`FJ R,地址`、`JMP 地址`。
- 函数边界：`函数名 SEGMENT`、`SEGMENT END`。

这些是项目自定义的汇编风格文本，不是已验证的 x86、ARM 或其他实际 ISA 输出。`ret` 分支当前只是加载返回表达式到 `R`，没有生成真实机器的返回指令。仓库也没有将该文本组装成可执行程序的步骤。

## 输入范围与语言支持边界

**关键字表包含某个词，并不等于整个编译器支持该语法。**精确的语法支持范围依赖尚未提交的 `grammar.txt`，不能只从注释或 Token 表恢复完整语言规范。

关键字表目前包含：

```text
int void while if else return float string
char break const do struct case for default
```

各阶段还存在以下差异：

| 项目 | 当前情况 |
| --- | --- |
| 标识符 | 词法扫描器支持下划线，但主窗口字符检查不允许 `_`；GUI 实验应使用英文字母开头、由字母和数字组成的名字 |
| 小数 | 扫描器有小数分支，但主窗口不允许 `.`；DAG 常量计算也是整数计算 |
| `&&`、`||`、数组括号 | 界符表有相关条目，但主窗口不允许 `&`、`|`、`[`、`]` |
| 字符和字符串 | 有 `S` Token 分支，但 `isS()` 缺少正常返回值；分析器没有像 `I/C` 那样提供 `S` 类型的特殊终结符匹配，不能声称已完整支持 |
| `float`、`char` 等类型 | 词法表有这些关键字，符号表动作和类型表主要围绕 `int` 实现 |
| 注释 | 扫描器没有跳过 `//` 或 `/* ... */` 注释的专门逻辑 |
| 预处理、函数调用、数组、结构体等 | 缺少足够的文法与端到端实现证据，不作为已支持能力列出 |

即便字符检查通过，也不意味着程序能通过语法分析、优化或目标代码生成。

## 内部表示与输出示例

以下示例**依据源码推导，用于解释表示格式，未进行端到端运行验证**。它们不是仓库自带测试，也不能替代缺失的文法。

### Token 串

以片段 `a=b+c;` 为例，在标识符表为空且扫描器完整读取此片段的前提下，词法表示为：

```text
(I 1),(P 11),(I 2),(P 8),(I 3),(P 13),
```

对应关系：`I[1]=a`、`I[2]=b`、`I[3]=c`；界符表中的 `=`、`+`、`;` 分别位于 11、8、13。实际容器用 0 基下标，展示地址采用 1 基编号。

这个片段用于解释词法结果；预测分析从 `<函数>` 开始，不能保证把它单独粘贴到 GUI 就能通过语法分析。

### 四元式

若文法针对该赋值依次安排以下四元式动作：

```text
PUSHi(a) → PUSHi(b) → PUSHi(c) → GEQadd → ASSI
```

且临时变量计数从 0 开始，则 `createquat` 生成：

```text
(+,b,c,t1)
(=,t1,_,a)
```

其中 `PUSHi(a)` 是便于阅读的动作描述；实际文法使用 `$PUSHi$`，传入值来自上一个已匹配的 Token。

界面会加上序号：

```text
(1) (+,b,c,t1)
(2) (=,t1,_,a)
```

`Quaternion.txt` 的文件格式在逗号后带空格，例如：

```text
(1)(+, b, c, t1)
(2)(=, t1, _, a)
```

优化文件则在四元式前加**基本块编号**，形式为 `块号 (op,arg1,arg2,result)`；此编号不是原始四元式的行号。`calcu("+", "2", "3")` 会得到字符串 `"5"`，但完整优化结果还受基本块划分、标记分配和当前实现问题影响，本文不提供未经验证的完整优化前后对照。

### 目标指令格式

当 `fillObj()` 接收到加法四元式、寄存器为空且指令计数为初值时，对应生成分支写出的指令形式为：

```text
0 LD R,b
1 add R,c
```

这只是单条四元式对应分支的源码推导。完整程序中的编号、存储指令和跳转取决于前置指令、寄存器状态及活跃信息，不能将此片段当作整条编译链的实测输出。

## 已知限制与排查方法

### 运行准备与显示问题

| 现象 | 检查方向 |
| --- | --- |
| 无法打开 `grammar.txt` | 补齐原始文法，检查运行工作目录；仓库本身未提供此文件 |
| 无法写出结果，符号表页为空 | 检查 `TextFile` 是否存在且可写；符号表导出失败会提前返回，界面用的结果数组也可能未填充 |
| 语法结果页为空 | `First.txt` 缺少生成逻辑；首次读取失败会阻止继续加载 FOLLOW/SELECT |
| 找不到 `ObjectCode.h` 或 `Qstring` | 代码引用大小写与 `objectcode.h`、`QString` 不一致，在区分大小写的文件系统上需要统一 |
| Linux/macOS 下输出路径异常 | 文法读取和优化文件写入含 Windows 反斜杠路径；还需统一 `SElect.txt` 与 `Select.txt` 的大小写 |
| 修改输入后结果未更新 | 需要重新点击“确定”，仅点击“下一步”不会重新分析 |

### 算法实现的当前限制

以下问题来自源码检查，是解释运行结果时需要考虑的实现边界：

- **文法加载失败未被上层处理。**`AN()` 忽略 `GetLL1Table()` 的返回值；缺失文件和非 LL(1) 文法的失败不能保证安全传播到界面。
- **状态重置不完整。**`createquat::clear()` 只重置计数和当前临时名，没有清空整个四元式数组或语义栈；`WordAna::clear()` 没有清空字符串表和全局词法错误标志。连续编译不同输入可能受上一次状态影响，排查时可先重启程序。
- **数字 Token 可能重复展示。**`scan()` 对数字先调用 `isC()` 检查，再调用一次计算前进长度；`isC()` 本身会追加 Token，因此展示串可能出现重复常数项。
- **字符串扫描不完整。**`WordAna::isS()` 声明返回 `int`，正常路径却没有返回扫描长度，不应依赖字符/字符串实验的结果。
- **基本块划分存在越界风险。**`optimize::divide()` 在循环中重新声明了 `i`，循环后的外层 `i` 仍为 0，随后访问 `qua[i-1]`。这会触发未定义行为，影响优化乃至完整流程的稳定性。
- **容量与格式有固定上限。**原始四元式、临时名和 DAG 数组使用 100 的固定长度，基本块容器为 `Block[15]`，缺少完整边界检查；目标代码读取器又只提取块号首字符，无法可靠处理两位数块号。这些数字不应视作已经验证的安全输入上限。
- **临时变量识别较粗糙。**优化器以“字母开头且第二个字符为 1–9”判断临时变量，而不是严格匹配 `t` 加数字；例如用户变量 `a1` 也可能被误分类。
- **活跃信息及后端仍需验证。**`activeinf()` 从四元式最后一个左括号向前扫描，普通未标注四元式的逗号在其右侧，因此预期的活跃标注可能没有生效；不要把该实现描述为已验证正确的活跃变量分析。

项目没有提供自动化测试、完整源语言样例、可执行目标代码规范或性能基准。扩展语言时，应同时检查输入字符白名单、Token 表、文法、符号表动作、四元式生成、优化分类和目标代码映射，而不只是向关键字表添加词条。
